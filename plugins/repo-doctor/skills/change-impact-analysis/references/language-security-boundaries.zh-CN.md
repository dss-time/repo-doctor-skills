# 按语言选择的安全规则与执行边界

## 选择适用规则
根据仓库证据识别源码语言、运行时、构建配置、部署环境和原生依赖。混合项目按组件选择，不能只看扩展名；未知条件明确记录。只应用与任务相关的检查，检查深度与变更相称，不遍历所有语言清单，也不自动安装工具链。

| 组件 | 相关检查与条件性验证 |
| --- | --- |
| JavaScript / TypeScript | 服务端授权、注入、原型污染、路径边界、异步竞态、静态类型之外的运行时验证。纯 JS 不套用手动 free、指针所有权或 C 整数溢出清单；原生扩展单独审查。 |
| Python | 参数化查询、不安全反序列化、命令构造、路径处理、授权和并发。纯 Python 不套用手动内存管理清单。 |
| Java / .NET | 对象级授权、反序列化、进程执行、资源释放、并发及框架安全配置；原生互操作作为独立边界。 |
| Go | 切片边界、错误处理、协程竞态、取消和资源生命周期；指针运算仅针对 unsafe/cgo 边界。 |
| Rust | 安全 Rust 仍需检查授权与逻辑。存在 unsafe/FFI 时检查其不变量、跨边界所有权及相关并发；不将安全 Rust 等同于应用安全。 |
| C / C++ | 缓冲区大小、分配或复制前的整数转换/溢出、所有权、生命周期、释放后使用、重复释放、未定义行为及并发。编译器诊断和 sanitizer 仅用于支持且获授权的环境。 |
| 嵌入式 / 固件 | 仅在实际存在时增加 ISR、DMA、RTOS、看门狗、时序和硬件故障安全检查。不得仅为验证审查而刷写或驱动硬件。 |

共享原则包括最小权限、可信授权、副作用前验证、保密性与失败关闭，但具体证据和测试随语言变化。缺少工具或硬件意味着未验证，不能作为安全通过的依据。

## 安全风险分流
对相关变更识别认证、对象/租户授权、攻击者输入到敏感操作的数据流、秘密、文件/网络/进程边界及特权或破坏性副作用。将有依据的安全风险带入既有协调风险/证据契约；没有关键词不代表没有风险。普通非安全任务不自动扩大为完整安全审计。保持安全专项审查显式调用以及现有权限不变。

## 运行时与组件选择
先识别相关组件再选择规则。浏览器 JS 在相关边界变化时检查 DOM/XSS、源隔离和浏览器存储；Node 服务端检查服务端授权、文件/进程/网络边界和运行时输入验证；Electron 检查主进程/渲染进程隔离、IPC 来源与载荷、preload 暴露、上下文隔离及实际存在的原生模块。TypeScript 类型不替代外部数据的运行时验证。
Python Web 框架需核查实际 ORM/查询 API、模板转义、中间件和部署配置。Java/.NET 根据框架/版本及实际安全中间件选择检查。C/C++ 识别编译器、目标 ABI、语言标准和 libc/RTOS。Rust 区分安全代码和 unsafe/FFI；Go 区分普通代码与 unsafe/cgo。不能仅凭依赖名称认定框架防护有效。
混合仓库按组件记录路径、语言、运行时/框架/版本证据、信任边界和适用检查。仅为变更组件及相关调用方/边界选择规则，缺少证据保持未知。原生内存规则仅用于原生组件或互操作契约。运行时规则指导具体检查，不强制引入新工具链或全量审计。
